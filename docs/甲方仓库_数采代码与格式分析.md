# 甲方 OrcaManipulation 仓库分析：数采代码 / 机器人 / 数据集格式

> 分析对象：`3rd-party/OrcaManipulation/`（官方仓库 `main` 分支副本）
> 分析日期：2026-10-01

---

## 一、结论速览

| 问题 | 结论 |
|---|---|
| **有没有数采代码？** | ✅ **有，而且很完整** —— 三种模式（脚本化 / 遥操作 / 回放）+ 两套存储格式 |
| **用的什么机器人？** | **OpenLoong** 与 **Tiangong2（天工二号）** 是主力；conf 里还配了 G1 OmniPicker、AR5、D12 |
| **保存什么格式？** | **两套并行**：① **HDF5**（自研，per-episode UUID 目录）② **LeRobot v3.0**（parquet + meta + MP4 视频） |

**一句话**：甲方已经有一套"机器人型号 × 存储格式"解耦的完整数采框架，**LeRobot 3.0 是官方原生支持的一等公民，不是待办项。**

## 二、数采代码在哪

### 2.1 三层结构

```
src/
├── dataCollectionManager/          数采管理器（调度层）
│   └── data_collection_manager.py
├── dataStorage/                    ★ 存储层（格式在这里决定）
│   ├── abstract_data_storage.py       抽象基类 + Hdf5DataStorage
│   ├── robot_profile.py               ★ 机器人型号抽象（格式无关）
│   ├── openloong_data_storage.py      OpenLoong HDF5
│   ├── tiangong_data_storage.py       Tiangong2 HDF5
│   ├── lerobot_data_storage.py        ★ LeRobot v3.0 通用层
│   ├── lerobot_openloong_storage.py   OpenLoong LeRobot
│   └── lerobot_tiangong_storage.py    Tiangong2 LeRobot
├── envs/dataCollection/
│   └── dataCollection_env.py
└── examples/dataCollection/        ★ 可直接跑的采集脚本
```

### 3.2 实际被数采脚本使用的

`--agent_name` 参数在各脚本里的取值：

| 脚本 | 可选机器人 |
|---|---|
| `data_collection_tele.py` | `openloong` \| `tiangong2` |
| `data_collection_tele_lerobot.py` | `openloong` \| `tiangong2` |
| `data_collection_aug.py` | `openloong` \| `tiangong2` |
| `data_collection_fluid_tele.py` | `openloong` \| `tiangong2` |
| `tiangong_collection_tele.py` | 固定 `tiangong2` |
| `AR5-5_07L_tele.py` | 固定 `AR5` |

**结论：数采主力是 `openloong` 和 `tiangong2` 两种双臂机器人。**

### 3.3 与我们机器人的关系

我们现场用的是 **`dual_arm_collaborative_service_robot_1`**，**不在**上面这些型号里。

> ⚠️ 这解释了一个一直存在的问题：**甲方的数采框架不能直接套在我们机器人上**，
> 因为 `RobotProfile` 是按型号写死的（关节名、末端 site 名、夹爪 actuator 名都不同）。
> 我们要么照着 `openloong_data_storage.py` 写一个我们机器人的 profile，
> 要么继续用我们自己那套 `collect.py`。

## 四、保存的数据集格式

### 4.1 HDF5 格式（自研）

**目录结构**（`Hdf5DataStorage`）：

```
<dataset_path>/<agent_name>/<level>/<uuid>/
├── record/proprio_stats.hdf5      ← 数据（默认名）
└── video/                         ← 视频（若配了相机）
```

- **每条 episode 一个 UUID 目录**（`uuid.uuid4()` 生成）
- HDF5 内部：`collection_data` 按 key 累加，`save_data` 时用 `gzip level 4` 压缩写出
- 额外写入 `task_info` / `scene_info`（JSON 字符串）

**字段**（以 OpenLoong 为例，来自 `obs_callback`）：

| 类别 | 内容 |
|---|---|
| `time_step` | `env.data.time`（每帧时间） |
| 关节 | 双臂 `qpos`（左右 arm joint_names） |
| 夹爪 | 夹爪 `qpos` + actuator 电机值 |
| 末端 | 双臂末端 site 的位置 + 四元数（**基座系 B**） |
| 其他 | 电机值、任务状态等 |

### 4.2 LeRobot v3.0 格式（官方原生支持）

**核心文件**：`src/dataStorage/lerobot_data_storage.py`（33 KB）
文件头明确写着：**"LeRobot v3.0 格式数据存储层"**。

**依赖**（`requirements.txt`）：

```
lerobot[dataset]>=0.6.1
pyarrow>=14.0.0
av>=15.0.0,<16          # 注意：PyAV 16+ 与 lerobot 0.6.1 不兼容，必须 <16
```

**输出结构**（标准 LeRobot 数据集）：

```
<--lerobot_out 目录>/
├── data/            parquet（每集一个文件）
├── videos/          MP4（ffmpeg 编码，每相机一路）
├── meta/            info.json / stats.json / tasks.parquet
│                    episodes/chunk-000/*.parquet  （v3.0 用 parquet，非 jsonl）
└── ...
```

**关键设计**：

| 项 | 做法 |
|---|---|
| 库 | `LeRobotDataset.create()` / `.resume()` |
| 落盘 | LeRobot 内部完成 **parquet + meta + ffmpeg 视频编码** |
| 图像 | **直接 `add_frame` 传真实图像**，由 LeRobot 编码，不用事后替换 |
| 多相机 | 每相机一个 `SingleFrameTask`，用 **future 同步保证 sim_idx 严格对齐** |
| 时间戳 | LeRobot 自动算 `timestamp = frame_index / fps`（**不用引擎时间**） |
| 帧率 | `--fps` 参数，默认 **30** |
| `repo_id` | `--repo_id`，默认 `local/manipulation` |
| 视频写入 | 每集后 close parquet writer 写 footer（**不 finalize 会导致 parquet 无法读取**） |

**State / Action 布局**（由 `RobotProfile.build_state()` 决定）：

| 机器人 | 维度 | 组成 |
|---|---|---|
| openloong | **16** | `l_pos(3) + l_quat_xyzw(4) + r_pos(3) + r_quat_xyzw(4) + l_grip(1) + r_grip(1)` |
| tiangong2 | **38** | `l_pos(3) + l_quat_xyzw(4) + r_pos(3) + r_quat_xyzw(4) + effector_motor_norm(24)` |

**action 约定**：`action[i] = state[i+1]`（next-step 移位，与 v5 及 **openpi 训练约定一致**）。

**安全校验**：`LeRobotDatasetWriter.create` 会拒绝把数据根目录设在
当前目录 `.` / 用户 home 等位置（因为 LeRobot 会清理 root，可能删掉源码）。

## 五、架构亮点：型号 × 格式 解耦

这是甲方设计得最值得学的一点：

```
        ┌─────────────────┐
        │  RobotProfile   │  机器人型号（关节名、site 名、归一化）
        │  （格式无关）    │  obs_callback / build_state /
        └────────┬────────┘  state_dim / state_names
                 │ 组合注入
        ┌────────▼────────┐
        │ AbstractData    │  存储格式（HDF5 / LeRobot）
        │ Storage         │  collection_data / save_data / clear_data
        └─────────────────┘
```

- **换机器人** → 只写一个 `RobotProfile`
- **换格式** → 只写一个 `DataStorage`
- 两者**通过组合**连接（注释里明确说明是为了**避免多重继承的 MRO 陷阱**）

## 六、对我们的启示

| 项 | 现状 | 建议 |
|---|---|---|
| 我们自己的采集 | `scripts/collect/`，HDF5，字段仿 `G1OmniPickerDataStorage` | 继续用，已验证可用 |
| LeRobot 3.0 | 之前以为要自己从零写 | **可以直接借鉴 `lerobot_data_storage.py`**，不用重造 |
| 机器人适配 | 我们是 `dual_arm_collaborative_service_robot_1`，甲方没有 | 若要用甲方框架，需照 `openloong` 写一份我们的 profile |
| 相机 | 我们未打通 | 甲方 LeRobot 层**多相机同步做得很完整**，可参考其 `SingleFrameTask` + future 方案 |
| 依赖坑 | — | **`av` 必须 `<16`**，否则与 lerobot 0.6.1 冲突 |
