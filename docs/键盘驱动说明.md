## 2. 设计要点

* **零依赖**：只用标准库 `msvcrt`（Windows 自带）。
* **同接口**：`left / right / lt / rt / dpad / held / pressed / released /
  pressed_any / rumble / connected / state` 全部对齐 `Gamepad`。
* **可注入**：键盘读取被抽成 `_read_frame()`，是**唯一**与真实硬件耦合的地方。
  测试替换它即可喂入受控按键序列，不需要真人按键。

## 4. 核心技术难点：msvcrt 不上报 key-up

`msvcrt` 只能读到「有键按下了」，**读不到「松开了」**。

解决办法：按住时 Windows 会以系统重复速率（约 30 Hz）连续产生字符，
于是用 **超时窗口 `hold_timeout`（默认 0.25 s）** 近似出「按住」语义：

* 本帧收到该键 → 刷新时间戳
* 连续 0.25 s 没再收到 → 视为已松开

### 4.1 方案B：把「按下」事件与重复速率解耦

如果直接用「比较两帧的按键位」检测上升沿，问题在于：
按键时系统重复速率一旦抖动（某帧恰好没收到该键），
`_down` 里该键会瞬时消失一帧，下一帧又回来 ——
就会被误判成「松开 → 又按下」，**采集状态机重复前进一格**。

因此改为三个集合协作：

| 集合 | 含义 |
|---|---|
| `_down` | 当前被认为按住的键（靠超时衰减） |
| `_held_prev` | 上一帧的 `_down`，用来发现「新按下」 |
| `_armed` | 已发现但**尚未被消费**的上升沿 |
| `_edge` | 本帧真正要报告的上升沿（`pressed()` 读它） |

规则只有三条：

1. 键从「不在 `_down`」变为「在 `_down`」→ 新上升沿，加入 `_armed`
2. 只有 `_read_frame()` 本帧**真正收到**的键才消费 `_armed`（进 `_edge`）
   —— 保证一次按下只报告一次；后续帧因重复而再收到该键时，`_armed` 已空
3. 键真正离开 `_down`（超时确认松开）→ 清掉 `_armed` 残留，
   这样下次按下才会重新产生上升沿

**效果**：一次按住 = 恰好一次 `pressed()`，与重复速率无关。
`test_keypad_realtime.py` 用真实 0.25 s 超时验证了这一点
（8 帧重复收到同一键 → 只报告 1 次；含丢帧抖动 → 仍只报告 1 次）。

## 5. 本次发现并修复的 3 个真实 bug

### Bug 1：`pressed()` 永远返回假（`keypad.py`）

`poll()` 里把 `self._prev_buttons` 赋成了**本帧**的 `buttons`，
而 `_state.buttons` 也是本帧 —— 两者恒等，`pressed()` 数学上必然为假。

**影响**：`teleop.py` 里的 `pad.pressed("BACK"/"X"/"Y"/"START")` 全部失效。

**修复**：在覆盖 `_state` **之前**取出旧的 `buttons` 作为 `_prev_buttons`。

### Bug 2：十字键 `DPAD_*` 别名缺失（`keypad.py`）

`_BUTTON_ALIASES` 里没有登记 `DPAD_UP/DOWN/LEFT/RIGHT`，
导致 `held("DPAD_DOWN")` / `pressed("DPAD_UP")` 这类调用一路返回 `False`。

**影响**：采集状态机若走 `pressed("DPAD_*")` 这条路会完全失灵。

**修复**：把四个方向登记进 `_BUTTON_ALIASES`。
（注意 `.dpad` 元组这条路径本来就是好的，两条路径现在保持一致。）

### Bug 3：十字键上/下**完全相反**（`keymap.py`）

`gamepad.py` 的权威定义是：

```python
dpad = ( RIGHT - LEFT ,  UP - DOWN )
```

即 **`dy = +1` 表示按下了「上」**。

但 `keymap.py` 写成了 `"down": int(dy > 0)` / `"up": int(dy < 0)`，
并且注释还写着「dy = +1 表示"下"」—— 与 `gamepad.py` 相反。

**影响（严重）**：按「上」触发 `arm`（待命），按「下」触发 `toggle_record`（录制），
与设计要求**正好反过来**。操作者会在相反的时刻进入待命/录制，
**静默地污染采集数据**。

**修复**：`"up": int(dy > 0)` / `"down": int(dy < 0)`，并修正注释。

> **教训**：`test_keymap.py` 原本也用了错误的约定
> （`pad.press(0, 1)  # dy=+1 为下`），所以测试一直是「绿的」，
> 却在验证一个错误的行为。测试和实现共享同一个错误假设时，测试无法发现问题。
> 现已同步修正测试。

## 补充（2026-09-26 晚）：按键无反应的根因与修复

### 现象

按 `--keyboard --flip-lr` 启动后，程序正常运行（输出 `pinch` 与 fps），
但**按键盘完全没反应**。

### 根因

`msvcrt.kbhit()` 读的是**控制台窗口**的键盘输入缓冲区。
而 `teleop.py` 默认 `render=True`，会弹出 MuJoCo/robosuite 的**渲染窗口**，
该窗口抢走了键盘焦点 → 控制台收不到任何按键 → `kbhit()` 恒为 0。

**手柄为什么没事**：手柄走 XInput（`XInputGetState`），
读的是设备状态，与窗口焦点无关，所以手柄不受影响。

### 修复

把按键读取从 `msvcrt` 换成 **`GetAsyncKeyState`**（通过 `ctypes` 调 `user32`）：

```python
_user32.GetAsyncKeyState.restype = ctypes.c_short
def key_down(name):
    return bool(_user32.GetAsyncKeyState(VK[name]) & 0x8000)
```

它读的是**全局**键盘状态，与焦点无关，因此渲染窗口抢焦点也能正常读到按键。

### 附带的好处

`GetAsyncKeyState` 的高位（`0x8000`）直接表示「当前是否按住」，
因此**能真正读到 key-up**，不再需要靠 0.25s 超时去猜「松手」：

| | 旧（msvcrt + 超时窗口） | 新（GetAsyncKeyState） |
|---|---|---|
| 渲染窗口抢焦点 | ❌ 完全失灵 | ✅ 正常 |
| 松手滑行 | ⚠️ 会多走约 0.25s | ✅ 松手立即停 |
| 按键重复速率影响 | ⚠️ 需方案B 兜底 | ✅ 无影响 |

**方案B 的边沿检测逻辑保留**——它保证了「一次按住 = 恰好一次 `pressed()`」，
这个保证在新版下依然成立且仍然必要。
