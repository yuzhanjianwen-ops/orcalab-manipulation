排查日期：2026-10-15　环境：OrcaStudio 26.8.1 / `orcalab281`
产出脚本：`scripts/collect/_decide_pose_render.py`、`_decide_two_renderers.py`、`_search_head_pose.py`、`_grid_head_pose.py`、`_verify_cam_fix.py`

## 一、一句话结论

**你要的构图（画面里有桌子、有夹爪）就是编辑器视口 idx1 / idx2 / idx3 的画面，
它们本身没问题；问题出在"采集链路用的是另一套相机位姿"。**

验收实测（同一时刻三台相机，左右逐格对比）：

| 视口 idx | 相机 | 编辑器视口 vs Studio 离屏渲染(同一位姿) | 判定 |
|---|---|---|---|
| 1 | `camera_head` | diff = 150.2 | **FAIL**（相机被包在机器人头部外壳里 → 全黑） |
| 2 | `camera_left` | diff = 23.9 | PASS |
| 3 | `camera_right` | diff = 22.9 | PASS |

结论：**左右腕相机两条链路一致；头部相机 `camera_head` 不一致——它的实际安装位姿让它落在头部外壳内部。**
而头部相机恰恰是唯一能同时拍到「桌子 + 托盘 + 药品 + 夹爪」的那台（见 `_fov_probe/poseRender/screen_idx1.png`）。

## 二、证据链

### 1. 你要的构图长什么样（目标）
`_fov_probe/poseRender/screen_idx1.png` —— 编辑器视口 idx1（`camera_head`）：
干净的白桌面 + 木格托盘 + 药瓶 + 药盒，构图完整。**这张就是采集应该拿到的画面。**

### 2. 同一个世界位姿，Studio 离屏渲染出来的是"头部外壳内壁"
`_fov_probe/poseRender/pose_render_montage.png`（左=编辑器屏幕，右=引擎按同一世界位姿渲染）
- idx0 自由相机：两边一致（都拍到桌子）
- idx2 / idx3 腕部相机：两边一致（都拍到夹爪）
- **idx1 头部相机：左边是桌面，右边是全黑**

### 3. 头部相机为什么全黑 —— 它被"埋"在头壳里
`_fov_probe/headPoseSearch/head_pose_search_montage.png`
以报告位姿为原点，沿 x/y/z 各挪 ±0.3 m 渲染 13 张：

| 偏移 | 画面 |
|---|---|
| 原位 (0,0,0) | **全黑**（在头壳内） |
| -0.3 y / +0.3 z / -0.3 x / +0.3 y | **都能看到桌面 + 托盘 + 药品**，与编辑器视口构图接近 |
| +0.6 x | 从外侧看到机器人的白色壳体柱 |

→ 相机只要离开原位约 0.3 m 就能得到你要的构图。**这说明渲染器本身没问题，是相机位置问题。**

### 4. 和"机器人 scale = 1.6954"高度吻合
布局文件 `D:\OTHERS\OrcaLab\SimpleMovement\camera10_11.json` 第 100–116 行：

```json
"path": "/dual_arm_collaborative_service_robot_1",
"transform": { "position": [18.464, -3.3896, 0.0383], "scale": 1.695356845855713 },
"asset_path": "assets/e071469a36d3c8aa/default_project/prefabs/g1_omnipicker_usda"
```

三台机载相机挂在这个被缩放 1.6954 倍的子树里。以头部相机为例：
- 报告世界位姿 `[18.057, -3.3775, 2.1156]`，机器人原点 `[18.464, -3.3896, 0.0383]`
- 相对距离 `|d| = 2.117 m`
- 实测需要补偿的量级 `1.11 / 张`（网格搜索）→ `|Δ| ≈ 0.83 m`
- 而 `(1 − 1/1.6954) × |d| = 0.868 m` —— **吻合到 5% 以内**

→ 支持判断：**相机的世界位姿在渲染侧没有把父节点的 scale 正确乘进相机偏移**，
导致相机落在头壳内部，而编辑器视口用的显示位姿是正确的。

## 三、修复方案

### 方案 A（最小改动，推荐先试）
在 OrcaStudio 里选中 `camera_head` 这台相机，沿它自己的视线方向往外挪：

- 实测 `-y 方向 0.3 m` 或 `+z 方向 0.3 m` 都能得到桌面构图；
- 挪完保存场景，跑验收脚本确认。

```bash
cd D:\OTHERS\projects\orcalab-manipulation\scripts\collect
python _verify_cam_fix.py
```

### 方案 B（根治，推荐）
**在场景根节点下新建一台相机**（不要挂在机器人子树里），摆在头部视角位置。

原因：根节点下的相机 `scale = 1.0`，不继承机器人的 1.6954，引擎侧和 Studio 侧算出来的位姿就一致了
（场景里已有的 `/head_camera_1`、`/wrist_camera_l`、`/wrist_camera_r` 就是这种根节点相机，
但 `/head_camera_1` 的朝向配错了，实际在拍天空，需要在 Studio 里改朝向）。

### 验证方法
改完资产/场景后跑：

```bash
python _verify_cam_fix.py                  # 直接验收
python _verify_cam_fix.py --offset 0,-0.3,0  # 不改资产，先看挪 0.3m 的效果
python _verify_cam_fix.py --idx 1          # 只验收头部相机
```

输出 `_fov_probe/verify/verify_montage.png`：左格编辑器视口、右格引擎离屏渲染，
`diff < 40` 记 PASS，`~150` 说明仍被遮挡。

## 四、两个必须知道的工程约束

1. **离屏渲染很慢**：实测 `get_view_png_from_transform` **1.11 s/张**（250 张平均）。
   所以"用指定位姿逐帧渲染"这条路只能做 ~0.9 fps 的慢速采样，
   **做不了 30 Hz 遥操作数据采集**。
2. **30 fps 只有 WS 推流这一条快路**（640×480 @ 7070/7080/7090）。
   而它的相机位姿是错的（见 §2.5）。
   → **所以必须修资产侧相机安装，才是唯一正解**；纯软件侧绕不过去。
3. `ncam = 0`：引擎相机不是靠 MuJoCo `<camera>` 元素，而是靠 Studio 侧的
   `camera_head_body1/2` 等占位 body + `SetCameraSensorInfo` 激活。
   修改相机位置要在 Studio 里改这些相机实体，改 MJCF 无效。
